# MCP servers are globally visible with agent-level exclusions

CDF's original MCP model was an explicit mount: an Agent only saw MCP servers whitelisted in `agent_mcp_servers`, and an unmounted server was invisible. Issue #70 replaces this with Claude Code's global-visibility semantics, extending the ADR 0012 principle from Skills to MCP: every configured MCP server is visible to every Agent by default, and an Agent-level **MCP Server Exclusion** hides specific servers from a specific Agent. Exclusion is the exception, not a grant — a newly configured server is immediately visible to all Agents with no per-Agent maintenance.

Decisions bundled with the visibility flip:

- **Exclusion is server-granular, not tool-granular.** Tool-level exclusion would require connecting to a server at Agent-edit time just to enumerate its tools, coupling configuration UI to connection state and breaking offline-first. Per-tool blocking, if ever needed, layers on later as a permission concern.
- **Exclusion is a flat list, not a Skill-style multi-state override.** MCP tools have no progressive disclosure, so `name-only` / `user-invocable-only` states have no implementable meaning. Copying the four-state Skill Override shape would be false symmetry.
- **Existing `agent_mcp_servers` whitelist data is dropped, not inverted.** Same rationale as ADR 0012's no-migration stance: the product hasn't shipped, and old bindings reflect what the whitelist model forced users to do, not an intent to exclude everything else. Inverting would freeze meaningless mass-exclusion records into the new model.
- **Connections decouple from Agents.** The per-Agent MCP client cache (keyed by `agentId`) becomes a shared connection layer keyed by global server config; Agent-level difference is a tool-list filter, not a separate connection. Under global visibility, per-Agent connections would spawn one child process per Agent per stdio server for identical server sets. Exclusions never trigger reconnects. If a stateful server ever needs an exclusive connection, that is an opt-in server declaration later.
- **MCP tool calls enter the approval boundary.** Previously the explicit mount act was the trust grant, and MCP tools bypassed `interruptOn` entirely in every approval mode. Removing the mount removes that gate, so the same change that removes it must add the replacement: in non-bypass approval modes MCP tool calls are interrupted (approve/reject), matching Claude Code's default of prompting for MCP tools. Per-call prompting with no memory is accepted noise; a per-server trust/allowlist mechanism (the shape of Claude Code's `mcp__server` allow rules) is a follow-up issue, not part of this change. PDF recovery gets no exemption — plan-level confirmation (ADR 0026) is not per-tool authorization, and a run-level approval bypass would make the new boundary negotiable in its first release.

Considered and rejected: keeping default-invisible with no change (contradicts ADR 0012's principle and issue #70's goal); removing per-Agent control entirely (loses the only tool-surface narrowing lever); and a discoverable-directory-plus-on-demand-connection model (token savings belong to a deferred-tool-loading mechanism, as in Claude Code's MCP tool search — an orthogonal concern that should not be entangled with the visibility model).

Consequence for PDF recovery (ADR 0043): an Agent's visible tool list — global set minus its exclusions minus unconnected servers — is the ground truth for capability discovery, which is exactly why agent-reported capability evidence needs no runtime metadata export.
