# Knowledge Entry schema is minimal and extensible

CDF will require every Knowledge Entry to carry a small managed frontmatter schema (`id`, `title`, `tags`, `created_at`, `updated_at`, and structured `source`) while preserving any additional OKF or domain-specific fields during updates. CRUD APIs identify entries by Knowledge Base-relative Markdown paths rather than frontmatter `id`, because the OKF source of truth is a file tree and files may be moved or edited outside CDF. Agent read/update/delete behavior reuses the existing file tools, while CDF adds OKF-aware search and create tools so Agents can discover entries and create new entries through code-level schema, path, collision, and safety guards. Search matches user-facing knowledge text (`title`, `tags`, selected `source` text fields, and Markdown body), while dates are structured filters and sort keys across entry creation, entry update, and source date. CDF initializes OKF reserved files `index.md` and `log.md`, but they are not Knowledge Entries: entry CRUD and search/list exclude them, while Agents may maintain `log.md` through ordinary file tools as a best-effort knowledge log rather than a guaranteed audit trail. This keeps CRUD, filtering, sorting, and Agent Tool contracts stable without turning the Knowledge Base into a closed schema that would block Paper Library and other Scene-specific entry types.

CDF follows a wide-read, strict-write rule for Knowledge Entries: list/search/read tolerate hand-authored Markdown files with incomplete managed metadata and report warnings, while create/update writes a complete minimal schema and preserves unknown frontmatter fields. Entry creation may accept a caller-provided relative Markdown path, but CDF owns path normalization, reserved-file rejection, project-root containment, and collision handling.

Agent-created Knowledge Entries use `source.type: "agent"` by default unless the Agent supplies a more specific source such as `url` or `paper`; renderer/user-created entries may continue to default to `manual`. `knowledge_create` does not automatically append to `log.md`; the tool response and Skill guidance should tell Agents to append a brief log note through ordinary file tools only when the addition, import, or reorganization is meaningful.

Knowledge Base usage guidance is Skill-driven rather than always injected into every Agent runtime prompt or exposed as a Project settings toggle. CDF should provide an internal/global Knowledge Base Skill that teaches the Agent how to enable and use the Knowledge Base when the user asks for it. Enabling a Project Knowledge Base is an Agent-executed initialization workflow: check or create `.cdf/knowledge/`, ensure `index.md` and `log.md`, and append only a short Skill trigger note into a CDF-managed block in the Project `AGENTS.md`. The managed block should tell future Agents when to use the Knowledge Base Skill, not duplicate the full operating manual. It should use explicit markers such as `<!-- CDF:knowledge-base:start -->` and `<!-- CDF:knowledge-base:end -->` so CDF/Agents can detect or update their own note without rewriting the user's unrelated project instructions.

The `AGENTS.md` managed block is maintained by the Agent through ordinary file tools as part of the Knowledge Base Skill workflow; CDF does not need a separate `enableKnowledgeBase` application API for this. `knowledge_create` remains independent of the managed block: it may safely initialize `.cdf/knowledge/` and create an entry even if the Project has not yet recorded the Knowledge Base trigger note in `AGENTS.md`, because the tool's job is safe entry creation rather than Project state management.
