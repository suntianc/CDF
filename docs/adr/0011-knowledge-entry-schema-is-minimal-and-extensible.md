# Knowledge Entry schema is minimal and extensible

CDF will require every Knowledge Entry to carry a small managed frontmatter schema (`id`, `title`, `tags`, `created_at`, `updated_at`, and structured `source`) while preserving any additional OKF or domain-specific fields during updates. CRUD APIs identify entries by Knowledge Base-relative Markdown paths rather than frontmatter `id`, because the OKF source of truth is a file tree and files may be moved or edited outside CDF. Agent write/read behavior reuses the existing file tools; CDF only adds an OKF-aware list/search tool so Agents can discover entries by frontmatter and body content without duplicating generic file CRUD. Search matches user-facing knowledge text (`title`, `tags`, selected `source` text fields, and Markdown body), while dates are structured filters and sort keys across entry creation, entry update, and source date. CDF initializes OKF reserved files `index.md` and `log.md`, but they are not Knowledge Entries: entry CRUD and search/list exclude them, while Agents may maintain `log.md` through ordinary file tools as a best-effort knowledge log rather than a guaranteed audit trail. This keeps CRUD, filtering, sorting, and Agent Tool contracts stable without turning the Knowledge Base into a closed schema that would block Paper Library and other Scene-specific entry types.

CDF follows a wide-read, strict-write rule for Knowledge Entries: list/search/read tolerate hand-authored Markdown files with incomplete managed metadata and report warnings, while create/update writes a complete minimal schema and preserves unknown frontmatter fields. Entry creation may accept a caller-provided relative Markdown path, but CDF owns path normalization, reserved-file rejection, project-root containment, and collision handling.
