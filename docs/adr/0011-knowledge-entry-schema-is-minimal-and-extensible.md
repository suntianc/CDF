# Knowledge Entry schema follows OKF frontmatter

CDF treats the Knowledge Base as an OKF-style file tree: `.cdf/knowledge/` contains Markdown Concept Documents with YAML frontmatter, while `index.md` and `log.md` are reserved files and are not Knowledge Entries. CDF should not describe `source` or `source.type` as OKF fields. OKF requires the frontmatter `type` field and recommends fields such as `title`, `description`, `resource`, `tags`, and `timestamp`; CDF-created entries should align with that shape.

CDF follows a wide-read, strict-write rule. Read/list/search tolerate hand-authored Markdown files with incomplete metadata and report warnings, while create/update writes OKF-aligned metadata: `type`, `title`, optional `description`, optional `resource`, `tags`, and `timestamp`. CDF preserves unknown frontmatter fields during updates so project-specific extensions and legacy fields are not lost.

CDF CRUD APIs identify entries by Knowledge Base-relative Markdown paths rather than frontmatter IDs, because the OKF source of truth is the file tree and files may be moved or edited outside CDF. Entry creation may accept a caller-provided relative Markdown path, but CDF owns path normalization, reserved-file rejection, project-root containment, and collision handling.

Agent read/update/delete behavior reuses the existing file tools. CDF adds OKF-aware `knowledge_search` and `knowledge_create` tools so Agents can discover entries and create new entries through code-level schema, path, collision, and safety guards. `knowledge_create` must not default to `source.type: "agent"` because `source` is not a CDF-managed OKF field and the writer is not the knowledge source. If CDF later needs writer provenance, it should use a separate CDF extension field instead of overloading OKF source semantics.

Knowledge Base usage guidance is Skill-driven rather than always injected into every Agent runtime prompt or exposed as a Project settings toggle. Enabling a Project Knowledge Base is an Agent-executed initialization workflow: check or create `.cdf/knowledge/`, ensure `index.md` and `log.md`, and append only a short Skill trigger note into a CDF-managed block in the Project `AGENTS.md`. The managed block should tell future Agents when to use the Knowledge Base Skill, not duplicate the full operating manual. It should use explicit markers such as `<!-- CDF:knowledge-base:start -->` and `<!-- CDF:knowledge-base:end -->` so CDF/Agents can detect or update their own note without rewriting the user's unrelated project instructions.

The `AGENTS.md` managed block is maintained by the Agent through ordinary file tools as part of the Knowledge Base Skill workflow; CDF does not need a separate `enableKnowledgeBase` application API for this. `knowledge_create` remains independent of the managed block: it may safely initialize `.cdf/knowledge/` and create an entry even if the Project has not yet recorded the Knowledge Base trigger note in `AGENTS.md`, because the tool's job is safe entry creation rather than Project state management.
